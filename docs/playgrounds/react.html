pdfnative-react playground

Edit the JSX on the left, click Render PDF, and a real PDF is produced in your browser by pdfnative-react. A custom React reconciler compiles the component tree into pdfnative blocks — no DOM, no headless browser, no upload. See the React guide for the full component reference.

How this demo loads. React 19, pdfnative-react 1.3.0, and pdfnative 1.8.0 are imported from the esm.sh CDN, and JSX is transpiled in-page with Babel standalone — purely to make a zero-install browser demo. In a real project you install the packages from npm (pdfnative-react ≥ 1.3.0 needs pdfnative ≥ 1.8.0) and your bundler handles JSX. This CDN tooling does not affect the published packages: the core pdfnative engine stays zero-dependency, and React is a peer dependency of pdfnative-react only.

Prefer tokens over JSX? Use a DocSpec

For AI agents and token-frugal authoring, pdfnative-react ships a compact DocSpec — plain data compiled by compileSpec() / renderSpecToBytes() with a published JSON Schema. The same invoice above becomes:

import { renderSpecToBytes } from 'pdfnative-react';

const bytes = renderSpecToBytes({
  title: 'Invoice #1024',
  footerText: 'Acme Inc',
  blocks: [
    ['h1', 'Invoice #1024'],
    ['p', 'Thank you for your business.'],
    ['table', { h: ['Item', 'Total'], r: [['Pro plan', '$49.00']], zebra: true }],
  ],
});

Since v1.2.0 a spec can also carry a top-level print field (bleed, page boxes, printer's marks) and every charts-v2 field; v1.3.0 adds typography, pdfx, outputIntent, creationDate, CMYK colours and print.marks.colourBars — all covered by the published JSON Schema, so an agent can self-validate a print-ready, dual-axis, byte-reproducible document before rendering, and lintSpec() runs the same 37 rules as lintDocument() on it. See the React guide for the full component and DocSpec reference.
